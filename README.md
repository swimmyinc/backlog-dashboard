# 保守工数ダッシュボード

Backlogの課題をクライアント別に集計する、招待制の社内ツールです。
Next.js（App Router）・React・SCSSで画面を構築し、静的出力と既存のCloudflare Worker APIを同一オリジンで配信します。D1に登録情報・取得結果・履歴を共有保存します。

## 利用者と権限

- 利用者の許可メールアドレスはCloudflare Accessの管理画面で登録します。アプリ内の招待・ユーザー管理はありません。
- `ADMIN_EMAILS` に登録されたメールの管理者だけが、クライアント基本情報、月次工数・繰越工数を登録・変更し、追加工数を記録できます。クライアントの削除も管理者に限ります。
- 一般利用者は、登録済みの全プロジェクトの閲覧、Backlog取得、履歴閲覧ができます。
- WorkerはAccess JWTの署名・発行元・対象アプリ・有効期限を検証し、そのJWTのメールで管理者を判定します。メールの単独ヘッダーでは権限を判定しません。
- Backlog APIキーは専用ユーザーのもの1つを全員で利用します。個人ごとのBacklog権限は引き継ぎません。

## ローカル起動

Node.js 24 LTSを推奨します。Node.js 22を使用する場合は22.13.0以上が必要です。依存バージョンは `package-lock.json` に固定しています。

```sh
npm ci
```

`.env` がなければ `.env.example` をコピーし、値を設定してください。

```dotenv
BACKLOG_API_KEY=専用ユーザーのAPIキー
BACKLOG_SPACE_URL=https://your-space.backlog.com
ADMIN_EMAILS=admin@example.test
LOCAL_USER_EMAIL=admin@example.test
```

- 接続先は1スペースです。HTTPSのオリジンだけを指定します。
- `ADMIN_EMAILS` はカンマ区切りで複数指定できます。空なら管理操作を許可しません。
- `LOCAL_USER_EMAIL` はローカルで再現する利用者です。管理者一覧にないメールを指定すると一般利用者になります。
- `.env` はGit・公開ファイルから除外します。`.dev.vars` は `.env` より優先されるため併用しないでください。
- 旧 `BACKLOG_ALLOWED_PROJECTS` は不要です。許可するプロジェクトは管理者が画面から登録します。

```sh
npm run dev
```

ローカルD1に未適用のマイグレーションだけを適用してから、Next.js・Worker API・同一オリジン用の開発ゲートウェイを起動します。既存の `.wrangler/state/` をそのまま使います。
[http://127.0.0.1:8787](http://127.0.0.1:8787) を開き、クライアントとプロジェクトキーまたは数値IDを登録してください。
登録時にBacklog APIでアクセス権を確認し、数値IDに統一します。同じプロジェクトの重複登録はできません。
実キーがない場合はプロジェクト登録・取得に失敗します。接続先も未設定の場合、画面に設定エラーを表示します。

開発コマンドは `LOCAL_DEV:true` を渡します。HTTPのループバックホストに限ってAccess認証を省略します。
`LOCAL_DEV` と `LOCAL_USER_EMAIL` は本番に登録しないでください。環境変数変更後は再起動します。
ローカルデータは `.wrangler/` に保存され、本番D1とは共有されません。

- ブラウザで開くURLは `http://127.0.0.1:8787` です。内部ではNext.jsが3000番、Worker APIが8789番を使います。すべてループバックに限定しています。
- React・SCSSの変更はFast Refreshで反映します。Worker変更はWranglerが反映します。終了は `Ctrl+C` で関連プロセスも停止します。
- ポートを変える場合は `PORT=8797 NEXT_DEV_PORT=3010 API_DEV_PORT=8799 npm run dev` のように別々の値を指定します。
- ゲートウェイは `/api/` をWorkerへ、それ以外をNext.jsへ転送します。異なるOriginやクロスサイト要求を許可する設定にはしていません。
- `.wrangler/dev.config.json` と `.wrangler/dev-assets/` は開発時の生成物です。編集やGit登録は不要です。
- `npm run preview` は本番相当の静的ビルドをWorkerで配信します。既定ポートが同じなので、`npm run dev` を停止してから実行します。
- Backlogのキーを `NEXT_PUBLIC_` 環境変数へ移さないでください。キーは引き続きWorkerだけで使用します。

## 本番の準備

以下は管理者による初回設定です。このコード変更だけでは本番環境は作成されません。

1. 対象Cloudflareアカウントで `npx wrangler login` を実行します。
2. `npx wrangler d1 create backlog-dashboard` で本番D1を作成します。
3. 新規環境の場合、`wrangler.jsonc` の `d1_databases[0].database_id` を作成したDBのIDに設定します。既存環境のIDを上書きしないでください。バインド名 `DB` は維持します。
4. `npx wrangler d1 migrations apply backlog-dashboard --remote` で本番スキーマを作成します。
5. `npm run deploy` でWorkerを作成します。この段階ではAccess設定不足のため画面は503で閉じます。
6. Cloudflare Zero Trustで公開ホスト全体を保護するAccessアプリを作成します。許可ポリシーの「Emails」に利用者を個別登録し、必要ならOne-time PINを有効にします。`/api/*` も保護対象に含めます。`workers.dev` を利用する場合はWorkerのアクセス制御からAccessを有効にしてください。
7. Workerの「Settings → Variables and Secrets」に次の値を登録して反映します。

| 設定名 | 種別 | 内容 |
| --- | --- | --- |
| `BACKLOG_API_KEY` | Secret | 専用BacklogユーザーのAPIキー1つ |
| `BACKLOG_SPACE_URL` | テキスト | `https://your-space.backlog.com` |
| `ADMIN_EMAILS` | テキスト | 管理者メールのカンマ区切り。Accessでも許可が必要 |
| `ACCESS_TEAM_DOMAIN` | テキスト | `https://your-team.cloudflareaccess.com` |
| `ACCESS_AUD` | テキスト | AccessアプリのApplication Audience (AUD) Tag |

8. 管理者でログインし、画面の「クライアント追加」から許可プロジェクトを登録し、詳細で対象月の月次工数・繰越工数を登録します。
9. 一般利用者での閲覧・取得、管理操作の拒否、許可していないメールのログイン拒否を確認します。

APIキーはWorkerだけが読み、`Backlog-API-Key` ヘッダーでBacklogへ送ります。ブラウザへ渡しません。
CLIで登録する場合は `npx wrangler secret put BACKLOG_API_KEY` の対話入力を利用してください。
`.env` は本番へ送信しません。`keep_vars: true` により管理画面で登録した通常変数を後続デプロイでも保持します。
Secretも通常のコード更新のたびに再登録する必要はありません。

## 月別工数と集計

クライアント基本情報とは別に、対象月（YYYY-MM）ごとに工数を管理します。一覧・詳細・サイドバーは同じ対象月を表示します。初期月は日本時間の当月です。

| 工数 | 定義 |
| --- | --- |
| 月次工数 | 対象月に使用できる工数。管理者が手入力 |
| 繰越工数 | 対象月に繰り越された工数。管理者が登録・調整。未登録月は条件に合う前月の残工数を初期表示。負数も可能 |
| 追加工数 | 対象月の追加明細の合計 |
| 確定工数 | 「完了」「処理中」「処理済み」の予定時間合計 |
| 予定工数 | 「未対応」の予定時間合計 |
| 使用可能工数 | 月次工数＋追加工数＋繰越工数 |
| 残工数 | 使用可能工数−確定工数 |
| 予定残工数 | 残工数−予定工数 |

- Backlogの `estimatedHours` だけで集計します。実績時間は新しい取得結果に保存せず、計算にも使いません。
- 開始日が対象月の1日〜末日に入る課題を取得します。未来の開始日でも対象月内なら含めます。開始日未設定・対象月外の課題は除外します。
- 種別名に「発注」を含む課題は除外します。上記4ステータス以外は集計しません。
- 予定時間未入力は `null` として保持し、集計時だけ0時間として扱います。明示的に入力された0時間とは区別します。状態や予定時間の変更は再取得時に反映します。
- 課題の「確定工数」「予定工数」には予定時間が入力された課題だけを表示します。未入力は「工数未入力の課題」にまとめ、予定時間を「未入力」と表示します。月・カスタム期間とも共通です。
- 各課題グループは見出し全体で開閉できます。確定・予定は初期状態で開き、未入力は閉じます。月・期間・クライアントの切り替え時に初期状態へ戻ります。
- 変更前の保存データは未入力も0時間に変換済みのため、そのままでは区別できません。正しい分類にはBacklogから再取得してください。再取得まで旧データの0時間は入力済みとして表示します。
- 月別設定がない月への取得・追加はできません。管理者が先に月次工数・繰越工数を登録します。未登録月の繰越工数は、同じクライアントの直前の月が取得済みで、残工数が0以上ならその値を入力欄に初期表示します。前月が未登録・未取得・残工数が負数の場合は0を初期表示します。
- 繰越工数の初期値は手動変更でき、「この月を登録」で保存されます。保存済みの値（0を含む）は維持し、前月の残工数が変わっても自動更新しません。
- 追加は正の工数と必須メモ（1〜1000文字）を指定し、記録日時・記録者とともに1件ずつ保存します。画面では記録日時を日本時間で表示します。今回の範囲では明細の個別編集・削除はありません。
- 入力工数は小数第2位に丸めます。月次工数は0〜100000時間、繰越工数は−100000〜100000時間、追加工数は1件につき0より大きく100000時間以下です。
- 未取得の月の確定工数・予定工数・残工数・予定残工数は「—」です。未取得を取得済みの0時間と混同しません。
- 同じ月の再取得ではその月の取得結果を置き換え、設定と追加明細を保持します。新方式は各月の最新結果を保存し、取得のたびに履歴を増やす方式ではありません。
- 月次工数・繰越工数の変更や追加明細の記録後は、保存済みの課題を使って残工数を再計算します。
- 他の利用者の変更は「一覧を更新」で読み込みます。古い更新番号での変更・取得は409で拒否し、同時更新で明細や取得結果を上書きしません。
- プロジェクト・接続スペースの変更では、新方式の課題取得結果を全月でクリアします。月別設定・追加明細・旧設定・旧履歴は保持します。
- クライアントを削除すると、月別設定・追加明細・取得結果・旧履歴も削除します。
- Backlog通信は30秒・100ページまで、取得結果のJSONは1MBまでです。途中の結果を成功として保存しません。

## カスタム期間と追加工数の操作

- 詳細画面の「月／カスタム期間」で切り替えます。カスタム期間は開始日・終了日を含む任意の期間で、課題の開始日を基準に集計します。
- カスタム期間では課題一覧・確定工数・予定工数のみ表示し、月次・繰越・追加の入力や使用可能工数・残工数・予定残工数は表示しません。
- カスタム集計は管理者・一般利用者とも実行できます。対象月の設定がなくても利用可能です。結果はブラウザの画面状態としてのみ保持し、DB、月別取得結果、クライアントの更新番号を変更しません。
- カスタム結果は期間変更・月モードへの切り替え・クライアント変更・再読み込みでクリアします。取得中の移動後に届いた応答は画面へ反映しません。
- 月モードの追加工数は「月次・繰越工数」エリアにまとめています。追加済み合計は常時表示し、「追加工数を入力」「追加履歴」は初期状態で閉じたアコーディオンです。入力は管理者のみ、履歴閲覧は全利用者が可能です。

## DB構成と既存データ

- `clients`: クライアント基本情報と更新番号。旧工数設定のJSONも保持。
- `client_months`: クライアントと対象月を主キーとする月次工数・繰越工数。
- `additional_hours`: 対象月に紐づく追加工数・メモ・記録日時・記録者。
- `monthly_results`: 対象月の課題取得結果・取得日時・取得者。集計値は設定と明細から計算。
- `history`: 旧方式の履歴。画面の「旧方式の設定・履歴」で参照でき、新しい月別集計には使いません。

`0002_monthly_hours.sql` は新しい3テーブルを追加するだけで、既存テーブルの内容を変更しません。旧履歴は更新日基準で、開始日や処理済み課題を保存していないため、正確な新方式への自動変換はできません。対象月の工数を登録し、Backlogから再取得してください。

ローカルでは `npm run db:migrate:local` または `npm run dev` で追加マイグレーションを適用します。本番適用時は既存データのバックアップを確保し、`npx wrangler d1 migrations apply backlog-dashboard --remote` を実行してから新コードをデプロイします。コード変更だけでは本番DBは更新されません。

## コマンドと構成

| コマンド | 内容 |
| --- | --- |
| `npm run dev` | ローカルD1の準備、Next.js＋Worker API＋開発ゲートウェイ起動 |
| `npm run db:migrate:local` | ローカルマイグレーションだけ適用 |
| `npm run build` | Next.jsを静的出力し、公開ファイルを `dist/` へ配置 |
| `npm run preview` | ビルドした画面をローカルWorkerで配信 |
| `npm run check` | 構文、静的ビルド、認証・API・D1・React画面のテスト |
| `npm run test:api` | Node.jsでAPI・認証・D1・生成ファイルを検証 |
| `npm run test:ui` | Vitest＋Testing LibraryでReact画面と一時D1への操作を検証 |
| `npm run deploy:check` | デプロイのドライラン |
| `npm run deploy` | 本番へデプロイ |

- `app/`: 日本語HTML、メタデータ、ダッシュボードの入口。
- `components/`: 一覧・詳細・月別工数・追加工数・課題・旧履歴・編集モーダル。
- `hooks/useDashboard.js`: データ取得、権限、画面状態、操作の直列化、移動後の応答無視。
- `lib/api.js` / `lib/format.js`: 同一オリジンAPI通信と表示用共通処理。
- `styles/globals.scss`: 共通の色・基本スタイル。
- `components/Dashboard.module.scss`: ダッシュボード内に限定したSCSS Modules。
- `worker.js`: Access認証、管理権限、入力検証、Backlog取得、静的ファイル配信。
- `store.js` / `migrations/`: D1保存、更新競合検出、履歴。React移行による変更はありません。
- `next.config.mjs` / `scripts/`: 静的出力とローカル開発の設定。
- `tests/`: 実キー・本番通信を使わない検証。D1はMiniflareの一時DBを使います。画面テストはReactをDOMに描画して、実際のWorker API・D1に対して操作します。

`.next/`、`out/`、`dist/` は生成物です。直接編集しないでください。ルートにあったVanilla版の `index.html`・`script.js`・`style.css` はReact・SCSSへの移植後に廃止しました。

## Next.js移行の範囲

- Next.js 16.4.2 / React 19.3.1 / Sass 1.106.0を使用しています。
- 本番ではNext.jsのサーバーを動かさず、静的出力＋Worker APIで動作します。SSR、Server Actions、Next.jsのAPI Routeは使用しません。
- 一覧と詳細は従来どおり同一ページ内で切り替えます。クライアント別URLの追加は今回の範囲に含めません。
- 工数定義、課題の開始日基準、カスタム集計の非保存、権限、更新番号による競合検出、旧履歴を維持しています。
- 現行の配色・配置・レスポンシブ表示と、追加工数入力のボタン型トグルを維持しています。
- DB構造の変更やデータの再登録は不要です。工数分類変更時の `0002_monthly_hours.sql` が本番未適用の場合のみ、リリース前に適用確認が必要です。
- 静的HTML・Next.jsのチャンクにもWorkerのAccess認証を適用します。生成ファイルだけを配信し、サーバーソース・ソースマップ・環境変数ファイルは公開しません。

### 本番切り替えまでの残タスク

1. `.env` のBacklog接続先・専用APIキーを設定し、実データで登録・月別取得・カスタム取得を確認する。
2. 本番D1のバックアップとマイグレーション適用状況、Accessの設定を確認する。
3. 本番への反映時に `npm run check` と `npm run deploy:check` を実行し、変更をレビュー・コミットする。
4. 本番デプロイ後、管理者・一般利用者の両方で表示・取得・保存を確認する。未認証ユーザーにはHTMLとチャンクが配信されないことも確認する。

この移行作業では本番デプロイ・本番DBの更新は行いません。追加の機能変更はこの構成を基準に実装します。
